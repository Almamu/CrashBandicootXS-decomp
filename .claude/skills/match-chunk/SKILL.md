# Matching a decomp-chunk issue

This repo tracks remaining decompilation work as GitHub issues generated by
`tools/chunk_remaining_work.py` - each one lists a contiguous run of
still-raw functions (one ROM address range, one `report_units.py`
category) sized to be a single self-contained unit of work. This skill is
the dispatcher: it does not replace the real per-function process in
[`docs/workflow.md`](../../../docs/workflow.md), it just gets you from "an
issue number" to "working through that process for the right functions."

## 0. Before anything else

Read these once per session if you haven't already, in order:
1. [`docs/workflow.md`](../../../docs/workflow.md) - the mandatory 8-step
   per-function loop. This is not optional style guidance.
2. [`docs/naming.md`](../../../docs/naming.md) - naming conventions, and
   when (rarely) to rename a `sub_XXXXXXXX`.
3. [`docs/matching.md`](../../../docs/matching.md) - the running log of
   every gotcha/compiler-quirk found so far. Skim it for the category
   you're about to work in; a lot of the ARM/Thumb-codegen quirks recur.

## 1. Get the chunk's function list

Given an issue number or URL:

```
gh issue view <N> --json title,body
```

The issue body has a fenced block listing the chunk's exact function
names, their ROM addresses, the source `asm/*.s` file(s), and the
`report_units.py` category. Treat that block as ground truth for *which*
functions to work on, but re-verify each one still exists in `asm/*.s`
before touching it - **the issue is a point-in-time snapshot; if another
PR already matched some of these functions, skip them and say so in your
own PR description rather than re-doing or reverting that work.**

If you don't have `gh` available or the issue is gone, re-run the
generator for the same category to get a current chunk:

```
python3 tools/chunk_remaining_work.py --max-functions 25 --md /tmp/chunks.md
```

and find the address range that matches the issue title.

## 2. Claim it (if working as a human-facing agent)

If a person is present and this is genuinely their repo, leave a comment
on the issue saying you're starting it (`gh issue comment <N> --body
"Starting on this."`) so two people/agents don't duplicate work. Skip this
step if you were asked to "just work on function X-Y" directly without an
issue existing yet.

## 3. Work the chunk, function by function

For **each** function in the chunk, in ROM address order:

1. Read its disassembly (`asm/<file>.s`) and understand what it does.
   Cross-reference `docs/rom_map.md` if the surrounding region has already
   been characterized - don't re-derive context that's already written
   down.
2. Write the C reconstruction. Prefer named structs/fields and
   `REG_*`/hardware-register macros over raw pointer-arithmetic casts
   (see the `matching_decomp_prefer_structs` convention: it's fine to
   fall back to raw offsets with a one-line comment when the function
   relies on `register ... asm("rN")` pins sensitive to exact expression
   shape).
3. Compile in isolation to iterate quickly (`arm-none-eabi-cpp` +
   `tools/agbcc/bin/agbcc`, see `docs/workflow.md` for the exact
   invocation), comparing disassembly against the ROM's raw bytes
   instruction-by-instruction. **This isolated compile is a diagnostic
   tool only - never treat it as proof of a match.**
4. Iterate (register pins, struct layout, statement order, `goto`s to
   force block ordering, the negative-constant bit-clear idiom, etc. -
   `docs/matching.md` has a large catalog of these) until it looks
   byte-identical.
5. If a function genuinely resists byte-exact matching after real effort
   but its semantics are fully understood: park it under
   `#if NON_MATCHING` / `.if NON_MATCHING == 0` with a doc comment
   explaining exactly what was tried and why it didn't work - never leave
   it as silently-wrong C, and never guess.
6. If a function's semantics aren't confidently understood (calls into
   deeply unexamined subsystems, contradictory field usage, etc.): leave
   it completely untouched in the raw `.s` file and say so plainly in
   your PR - don't force a low-confidence match or park.
7. If a function has **no caller anywhere in the ROM**, it's still real
   shipped code - match or park it exactly like any other function, then
   tag its doc comment `UNUSED - no caller anywhere in the ROM (checked
   asm/*.s, expected/*.s, src/**/*.c)`. Don't skip it or leave a vague
   "what is this for?" comment.

Once a function matches (or is parked/left raw with a clear reason), cut
its matched block out of the raw `asm/*.s` (parked/left-raw ones stay in
place, matched ones move to the right `src/**/*.c` file), update
`ldscript.txt` if you introduced or split a file, and update
`tools/report_units.py`'s `UNITS` list if the file/category boundary
changed.

## 4. Verify the whole chunk together, not function-by-function

After working through the chunk (or as far as you got), run the **full
clean verification cycle once** for the whole batch - not per function,
that wastes a rebuild per function for no extra confidence:

```
rm -rf build && make NON_MATCHING=1 report
rm -rf build crashbandicootxs.elf crashbandicootxs.gba crashbandicootxs.map && make compare
```

Only "La suma coincide" from `make compare` counts as a match. If it
fails, diagnose via the map-file address-shift method in
`docs/workflow.md` (byte offset → ROM address → cross-reference
`crashbandicootxs.map` → isolate which function regressed → diff raw
bytes directly with `objdump`) rather than guessing.

## 5. Update docs and commit

- `docs/matching.md`: append a section for this chunk following the
  existing per-function/per-batch write-up style (semantics, any
  compiler-quirk fixes, what got parked or left raw and why).
- `docs/status/<system>.md`: add matched functions to the file's list;
  add parked ones to its "Parked" section with a one-line summary.
- `python3 tools/report_units.py` to regenerate `objdiff.json` if you
  touched `UNITS`.
- Commit with a message describing what got matched/parked/left, in this
  project's established style (see recent `git log` for examples) -
  **create a new commit, never amend**, and follow the repo's standing
  git-safety rules (no force-push, no `--no-verify`, etc.).

## 6. Open the PR

```
gh pr create --title "Match <address range or short description>" --body "..."
```

The PR body should say plainly: which functions matched, which got
parked (with the one-line reason each), which were left untouched (with
why), and confirm the full clean `make compare` passed. Reference the
issue (`Closes #N`) only if **every** function in the chunk reached one
of matched/parked/left-untouched-with-reason - if you only got partway
through a big chunk, say so instead and leave the issue open (or comment
with progress) rather than closing it early.

## Notes for a fresh agent with no repo context

If you're starting cold (no prior conversation in this repo): read
`docs/workflow.md` end to end before touching anything, and read the
specific chunk's category notes in `docs/rom_map.md` and
`docs/matching.md` for context already established about that address
range - a lot of struct layouts and calling conventions are already
pinned down and referenced by name (`gUnknown_030012D8`,
`sub_803AD80`-family trampolines, `struct aabb`, etc.); don't re-derive
what's already written down.
