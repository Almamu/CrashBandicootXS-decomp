# Issue #19: `0x08015840`-`0x08016128` (actor)

GitHub issue #19 listed this chunk under the `graphics` label (from
`tools/chunk_remaining_work.py`'s automated guess), but every function in
it operates on the same "self" action-table object (`self+0xc` mgr table
pointer, `self+0x10` part pointer, `self+0x27`/`self+0x2f`/`self+0x31`
and `self+0x28`/`self+0x30`/`self+0x32` state/counter/table-index trio
pairs) already documented at length in `ctrl.c`/`action_ctrl_states.c`/
`action_ctrl_moves.c`/`action_ctrl.c` - the same recategorization several
other `graphics`-labeled chunks in this ROM region have needed (issues
#16, #17, #18, #22, #52, #58, #62). Filed under `docs/status/actor.md`,
not `graphics.md`.

This chunk sits directly after `action_ctrl.c`'s matched span (which
ends with the shared `SetActionCtrlModeAnim` trampoline-pair-plus-sentinel-store
helper this chunk's first function, `RestartActionCtrl`, calls) and after the
already-parked `ActionCtrlSetTargetAnim` right before it.

## Matched - `src/player/action_ctrl.c`

`RestartActionCtrl`-`RestartPlayerCtrl` (19 functions): a run of small accessors and
resetters on the "self" object's state-trio bytes (`self+0x27`/`0x2f`/
`0x31` and `self+0x28`/`0x30`/`0x32`), matching the shape already
established by `action_ctrl_moves.c`'s `StartActionCtrlHighJump`/`StartActionCtrlMaskHitJump`:

- `RestartActionCtrl`: fires the mgr trampoline pair (`SetActionCtrlModeAnim(self, 0,
  0x12, 0, 0)`), then resets both state trios.
- `DestroyActionCtrl`/`InitActionCtrl`: the same `gActionCtrlVtable`
  double-table-set idiom already documented for `DestroyBossCtrl`/
  `CreateBossCtrl` in `input_ctrl_queue.c` - `DestroyActionCtrl` re-points `self+0xc`
  at `gActionCtrlVtable` then tail-calls `DestroyCtrl` (which
  promptly resets it back to `gCtrlVtable`); `InitActionCtrl`
  resets via `InitCtrl`, re-points at `gActionCtrlVtable`, and
  calls `ResetActionCtrl` (the child-object field-reset constructor from
  `wumpa.c`) - confirming that function's own comment, which
  named this exact caller while it was still raw.
- `sub_80158AC`-`GetActionCtrlPrevState` (14 functions): trivial single/few-
  instruction getters and setters on `self+0x14`/`0x27`/`0x28`/`0x2d`/
  `0x2f`/`0x30`/`0x31`/`0x32` - all matched on the first attempt.
- `ResetPlayerCtrl`: a larger field reset (`self+8`/`0x10`/`0x14`/`0x18`/
  `0x1c`/`0x20`/`0x22`-`0x27`, plus the player's `+0x92`) needing the
  "running cursor pointer" register-pinning technique (see below).
- `RestartPlayerCtrl`: fires the mgr trampoline pair via `SetPlayerCtrlState(self, 0,
  0, 0, 0)` (a still-unmatched sibling of `SetActionCtrlModeAnim`, same 5-arg
  shape with a `0x7FFFFFFF` "don't update" sentinel convention seen at
  its other call sites in this chunk), then resets a similar field set
  to `ResetPlayerCtrl`.

## Matched - `src/player/swim_ctrl_drift.c`

`SetPlayerSwimDriftY`: a player-velocity-relative "record" writer. Computes a
Q14 rounded `((player->0x64^2 / 0x4000) + 4) * 3 / 2` timing value, then
compares `|player->0x64|` against `|arg2|` to decide whether the current
`gPlayer` record (`+0x54`/`+0x58`/`+0x5c`) gets the computed
value or a product-sign-selected combination of `arg1`/the computed
value. Non-adjacent to `action_ctrl.c` since the left-raw
`StartPlayerCtrlStroke`/`StartPlayerCtrlSpin`/`ApplyPlayerCtrlSwimDrift` sit between them.

Needed real register-pinning work, mirroring the shape ROM keeps: `self`
pinned to `r6`, `arg1` to `ip` (spilled out of the low registers - the
function has too many long-lived values, `self`/`arg2`/`vel`/`result`,
for the four callee-saved low registers plus `arg1`), `arg2` to `r5`,
the `gPlayer` pointer to `r3`, and the player's velocity field
to `r4`. Two techniques from `matching_decomp_register_pinning` applied
directly:

- The abs-value computations needed the classic `sign = x >> 31; abs =
  (x ^ sign) - sign` bit-trick spelled out explicitly in C (a plain
  `(x < 0) ? -x : x` ternary compiles to a different `neg`/`cmp`/`bge`
  idiom that doesn't match).
- **The final `result` value must NOT be pinned to `r7`** - confirmed
  again here, matching the existing note on `IsEntityInsideRect`
  (matching.md): pinning it explicitly dropped `r7` from the
  function's `push`/`pop` list entirely (a genuine miscompile, not just
  a mismatch) and produced the wrong final add/copy shape. Leaving
  `result` as a completely ordinary, unpinned local lets gcc's own
  allocator land it in `r7` by itself, matching the ROM exactly
  including the correct `push {r4, r5, r6, r7, lr}`/
  `pop {r4, r5, r6, r7}` prologue/epilogue.
- The two comparison branches (`absVel > absArg2`, and the inner
  `prod < 0`) both needed their C `if`/`else` arms ordered so the
  *ROM's actual branch instruction* (`ble`/`bge`, always branching
  *into* the less-common arm while the common arm falls through) comes
  out naturally - writing the condition as its own negation swaps which
  arm the compiler treats as the fallthrough.

`sub_8016046` (the ROM's disassembly labels it a function at
`0x08016046`, `non_word_aligned_thumb_func_start`, body `movs r0, r0`) -
**not real code**. `SetPlayerSwimDriftY`'s own body is 106 bytes (not a multiple
of 4), so its real end address `0x08016046` isn't 4-aligned; the two
bytes up to `0x08016048` (where `CheckPlayerCtrlTurn` starts, still raw) are
zero-fill alignment padding that this ROM's disassembly renders as
`movs r0, r0` (0x0000) - not a literal `adds r0, r0, #0` instruction.
This is the exact same situation already documented for `GetEntityPixelY`'s
gap in `docs/matching.md`: "always confirm a disassembly gotcha against
the raw ROM bytes, not just against how a tool chose to render them."
Nothing anywhere in `asm/*.s`/`expected/*.s`/`src/**/*.c` calls or
references `sub_8016046`, confirming it's genuinely just padding, not a
missed real function. `swim_ctrl_drift.c`'s own trailing
`asm(".align 2, 0")` directive (the same one every matched function in
this project gets) reproduces those exact two zero bytes automatically,
so no separate C function or symbol is needed for it - its "checkbox" is
handled by `SetPlayerSwimDriftY`'s own entry.

## Formerly parked (NAKED), now matched under old_agbcc - `src/player/swim_ctrl_stroke.c`

(History below; see "Later pass: old_agbcc" at the end for how they closed.)

A later pass (still issue #19) worked out full semantics for all three
of the jump-table dispatchers this doc originally left raw
(`StartPlayerCtrlStroke`/`StartPlayerCtrlSpin`/`ApplyPlayerCtrlSwimDrift`, ROM `0x080159F8`-
`0x08015FD0`, previously `asm/code_3_2_17_159f8.s` - now fully retired)
and attempted real C for all three:

- **`StartPlayerCtrlStroke`** (13-case jump table on `self+0x21`, a `self+8==4`
  fast path indexing a stack-copied 8-word table
  `gPlayerCtrlTurnSpeeds` by `part+0x30`, then per-case
  `part+0x60`/`part+0x64` velocity writes sign-selected by `part+0x28`
  bit 4, using the same goto-based shared-tail technique already
  established for `action_ctrl.c`) and **`StartPlayerCtrlSpin`** (a
  `self+8==4` fast path plus a second 13-case jump table on
  `self+0x21`, gated by a `part+0x68`-flag/`GetDpadDirection` D-pad-remap
  boolean, needing the `SetPlayerSwimDriftY`-style `/4`-with-rounding-
  adjustment idiom for several cases) both got real C reconstructions
  that matched almost every instruction on the first few attempts, but
  a recurring gcc-2.9 codegen gap resisted every technique tried: the
  ROM routes several `(x*3)>>2`-style computations through an extra
  scratch-register copy (e.g. `adds r5,r0,r5` / `adds r1,r5,#0` /
  `asrs r6,r1,#2` - three steps, the middle one a pure
  register-to-register copy) that this compiler's own register
  allocator collapses to two steps (computing straight into the final
  destination register) regardless of how the intermediate value was
  named, register-pinned (`register s32 t asm("r1")`), or reassigned
  in the C source. Two *other* gaps in the same functions - a `switch`
  bounds check fusing into a single `bhi`-style branch instead of the
  ROM's separate `bls`+`b` pair once the same `switch` also lowers to
  a jump table, and a `/4` vs `>>2` operator choice affecting whether
  the round-toward-zero `cmp;bge;add #3` adjustment gets emitted for a
  register-pinned (especially high-register `r8`) dividend - were
  successfully worked around, but the scratch-copy gap alone was
  enough to block a genuine match.
- **`ApplyPlayerCtrlSwimDrift`** (spawns a "kind 4" object via `SpawnEffectPart` on a
  1-in-128-frame RNG tick, then a 9-case jump table on a D-pad-remap
  result dispatching `SetPlayerSwimDriftX`/`SetPlayerSwimDriftY` calls with
  `(valB*3)>>2`/`(mag*3)>>2`-style timing values) hit the exact same
  scratch-copy gap in its own 4 tricky cases.

All three were transcribed instruction-for-instruction from the ROM
disassembly instead (the same escape hatch used for `ActionCtrlStateLand` in
`action_ctrl_land.c` and `MakeLinkHandshakeId`/`ResetLinkSessionState` in
`src/link/link_handshake.c`), verified byte-exact via direct machine-code
comparison against the frozen ROM disassembly and confirmed by a full
clean `make compare` ("La suma coincide"). `StartPlayerCtrlStroke`/`StartPlayerCtrlSpin`
live in `src/player/swim_ctrl_stroke.c`; `ApplyPlayerCtrlSwimDrift` is split into its
own file/unit, `src/player/swim_ctrl_stroke.c`, purely so each
`tools/report_units.py` unit's real ROM range stays self-contained -
none of the three count as "matched" (all three units carry
`base_object = None`).

- **`CheckPlayerCtrlTurn`** - a smaller (~50-instruction) dispatcher on `self+8`
  and the current joystick input state, calling `SetPlayerCtrlState` twice with
  a `0x7FFFFFFF`/`0x7FFFFFFF` sentinel pair. Matched later as real C
  (built with old_agbcc) together with issue #20 in
  `src/player/swim_ctrl.c`, see
  [issue-20-player-ctrl.md](./issue-20-player-ctrl.md).
  `asm/code_3_2_17_16048.s` is retired.

`tools/report_units.py`'s `UNITS` table keeps accurate real-address
boundaries through this whole span (`0x080159F8` through `0x08016048`)
regardless of which entries carry a real `base_object` vs `None`.

## Later pass: old_agbcc closes the three dispatchers

`StartPlayerCtrlStroke`, `StartPlayerCtrlSpin` and `ApplyPlayerCtrlSwimDrift` are plain C now, and
`swim_ctrl_stroke.o` are on the Makefile's `OLD_AGBCC_OBJS`.
`StartPlayerCtrlSpin` has the old_agbcc tell (`movs r0, #3; ldrb r1, [..];
ands r0, r1`), and `CheckPlayerCtrlTurn` right after this range was already
old_agbcc code (issue #20). Under old_agbcc all three match. Under the
current agbcc they are 8, 20 and 19 bytes off. The "scratch-register
copy" before each `>> 2` (`adds r5,r0,r5; adds r1,r5,#0; asrs r6,r1,#2`)
that kept them NAKED is simply what old_agbcc emits for `x * 3 / 4`.

What the C needed:

- **Unsigned magnitudes.** `speed` (`StartPlayerCtrlSpin`) is a `u16` and
  `mag`/`valB`/`valA` (`ApplyPlayerCtrlSwimDrift`) are `u16`/`u8`. gcc then knows
  `x * 3` is non-negative and divides by 4 with a plain `asr`. Only the
  negated values (`-speed * 3 / 4`) get the `cmp; bge; adds #3` rounding.
  The ROM's mix of rounded and unrounded divisions follows from that.
- **`SIGNED_X(t, v)` = `t->f28.flipX ? -(v) : (v)`.** gcc's fold()
  distributes `* 3 / 4` over the ternary, so each arm gets its own
  division, as in the ROM.
- **Case order.** The case bodies are written in the ROM's layout order
  (`StartPlayerCtrlStroke`: 1, 2, 4, 5, 7, 8, 10, 11, 6, 3, 0, 9, 12). The shared
  tails are gcc's cross-jumping, not gotos.
- **Register choice for a single store.** A few cases needed their value
  in a local first (`s32 v = SIGNED_X(...); target->speedX = v;`, or an
  explicit `if`/`else` on `flipX`) to get the ROM's registers.
- **`StartPlayerCtrlStroke` re-stores `target->tag`** (`ldrb`/`strb` of the same
  byte). A plain self-assignment is deleted, so it is a `volatile` store.
- **`ApplyPlayerCtrlSwimDrift`'s spawn** computes `x`, `y` and the `flipX` bit into
  locals before the `SpawnEffectPart` call, and clears bit 2 of the spawned
  object's `+0x0C` through a 1-bit bitfield (`movs r0, #5; negs r0, r0`
  is `~4`, not `~5` as the old transcription's comment said).

This closes issue #19: nothing in `0x08015840`-`0x08016128` is raw,
NAKED or `NON_MATCHING` any more.
