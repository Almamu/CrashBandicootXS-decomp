# Issue #19: `0x08015840`-`0x08016128` (actor)

GitHub issue #19 listed this chunk under the `graphics` label (from
`tools/chunk_remaining_work.py`'s automated guess), but every function in
it operates on the same "self" action-table object (`self+0xc` mgr table
pointer, `self+0x10` part pointer, `self+0x27`/`self+0x2f`/`self+0x31`
and `self+0x28`/`self+0x30`/`self+0x32` state/counter/table-index trio
pairs) already documented at length in `actor_part17.c`/`actor_part18.c`/
`actor_part38c.c`/`actor_part38d.c` - the same recategorization several
other `graphics`-labeled chunks in this ROM region have needed (issues
#16, #17, #18, #22, #52, #58, #62). Filed under `docs/status/actor.md`,
not `graphics.md`.

This chunk sits directly after `actor_part38d.c`'s matched span (which
ends with the shared `sub_8015780` trampoline-pair-plus-sentinel-store
helper this chunk's first function, `sub_8015840`, calls) and after the
already-parked `sub_80157C4` right before it.

## Matched - `src/graphics/actor_part57.c`

`sub_8015840`-`sub_80159A4` (19 functions): a run of small accessors and
resetters on the "self" object's state-trio bytes (`self+0x27`/`0x2f`/
`0x31` and `self+0x28`/`0x30`/`0x32`), matching the shape already
established by `actor_part38c.c`'s `sub_8015508`/`sub_8015558`:

- `sub_8015840`: fires the mgr trampoline pair (`sub_8015780(self, 0,
  0x12, 0, 0)`), then resets both state trios.
- `sub_8015878`/`sub_801588C`: the same `gStaticData_087E4224`
  double-table-set idiom already documented for `sub_8017A78`/
  `sub_8017A8C` in `actor_part27.c` - `sub_8015878` re-points `self+0xc`
  at `gStaticData_087E4224` then tail-calls `sub_800B8A8` (which
  promptly resets it back to `gStaticData_087E3E7C`); `sub_801588C`
  resets via `sub_800B8C8`, re-points at `gStaticData_087E4224`, and
  calls `sub_8011B90` (the child-object field-reset constructor from
  `actor_part39.c`) - confirming that function's own comment, which
  named this exact caller while it was still raw.
- `sub_80158AC`-`sub_8015950` (14 functions): trivial single/few-
  instruction getters and setters on `self+0x14`/`0x27`/`0x28`/`0x2d`/
  `0x2f`/`0x30`/`0x31`/`0x32` - all matched on the first attempt.
- `sub_8015958`: a larger field reset (`self+8`/`0x10`/`0x14`/`0x18`/
  `0x1c`/`0x20`/`0x22`-`0x27`, plus the player's `+0x92`) needing the
  "running cursor pointer" register-pinning technique (see below).
- `sub_80159A4`: fires the mgr trampoline pair via `sub_8017264(self, 0,
  0, 0, 0)` (a still-unmatched sibling of `sub_8015780`, same 5-arg
  shape with a `0x7FFFFFFF` "don't update" sentinel convention seen at
  its other call sites in this chunk), then resets a similar field set
  to `sub_8015958`.

## Matched - `src/graphics/actor_part57b.c`

`sub_8015FDC`: a player-velocity-relative "record" writer. Computes a
Q14 rounded `((player->0x64^2 / 0x4000) + 4) * 3 / 2` timing value, then
compares `|player->0x64|` against `|arg2|` to decide whether the current
`gUnknown_030012D8` record (`+0x54`/`+0x58`/`+0x5c`) gets the computed
value or a product-sign-selected combination of `arg1`/the computed
value. Non-adjacent to `actor_part57.c` since the left-raw
`sub_80159F8`/`sub_8015C6C`/`sub_8015DF8` sit between them.

Needed real register-pinning work, mirroring the shape ROM keeps: `self`
pinned to `r6`, `arg1` to `ip` (spilled out of the low registers - the
function has too many long-lived values, `self`/`arg2`/`vel`/`result`,
for the four callee-saved low registers plus `arg1`), `arg2` to `r5`,
the `gUnknown_030012D8` pointer to `r3`, and the player's velocity field
to `r4`. Two techniques from `matching_decomp_register_pinning` applied
directly:

- The abs-value computations needed the classic `sign = x >> 31; abs =
  (x ^ sign) - sign` bit-trick spelled out explicitly in C (a plain
  `(x < 0) ? -x : x` ternary compiles to a different `neg`/`cmp`/`bge`
  idiom that doesn't match).
- **The final `result` value must NOT be pinned to `r7`** - confirmed
  again here, matching the existing note on `sub_8007114`
  (matching.md): pinning it explicitly dropped `r7` from the
  function's `push`/`pop` list entirely (a genuine miscompile, not just
  a mismatch) and produced the wrong final add/copy shape. Leaving
  `result` as a completely ordinary, unpinned local lets gcc's own
  allocator land it in `r7` by itself, matching the ROM exactly
  including the correct `push {r4, r5, r6, r7, lr}`/
  `pop {r4, r5, r6, r7}` prologue/epilogue.
- The two comparison branches (`absVel > absArg2`, and the inner
  `prod < 0`) both needed their C `if`/`else` arms ordered so the
  *ROM's actual branch instruction* (`ble`/`bge`, always branching
  *into* the less-common arm while the common arm falls through) comes
  out naturally - writing the condition as its own negation swaps which
  arm the compiler treats as the fallthrough.

`sub_8016046` (the ROM's disassembly labels it a function at
`0x08016046`, `non_word_aligned_thumb_func_start`, body `movs r0, r0`) -
**not real code**. `sub_8015FDC`'s own body is 106 bytes (not a multiple
of 4), so its real end address `0x08016046` isn't 4-aligned; the two
bytes up to `0x08016048` (where `sub_8016048` starts, still raw) are
zero-fill alignment padding that this ROM's disassembly renders as
`movs r0, r0` (0x0000) - not a literal `adds r0, r0, #0` instruction.
This is the exact same situation already documented for `sub_8007364`'s
gap in `docs/matching.md`: "always confirm a disassembly gotcha against
the raw ROM bytes, not just against how a tool chose to render them."
Nothing anywhere in `asm/*.s`/`expected/*.s`/`src/**/*.c` calls or
references `sub_8016046`, confirming it's genuinely just padding, not a
missed real function. `actor_part57b.c`'s own trailing
`asm(".align 2, 0")` directive (the same one every matched function in
this project gets) reproduces those exact two zero bytes automatically,
so no separate C function or symbol is needed for it - its "checkbox" is
handled by `sub_8015FDC`'s own entry.

## Left raw - `asm/code_3_2_17_159f8.s` / `asm/code_3_2_17_16048.s`

- **`sub_80159F8`/`sub_8015C6C`/`sub_8015DF8`** - three large (40-100+
  instruction) jump-table state-machine dispatchers reading/writing the
  part object's `+0x60`/`+0x64` velocity fields and `self`'s
  `+0x21`/`+0x22` state bytes, gated on `gStaticData_0816C090`/
  `gStaticData_0816BF20`-style per-case tables, calling into
  `sub_8017264`/`sub_8025BAC`/`sub_80172D0`/`sub_8015FDC`/`sub_80087C0`/
  `sub_80087B4`/`sub_800872C`. Each is mechanically understandable at
  the level of "what field gets written in each case" but not yet
  confirmed to a byte-exact-reconstruction level of confidence within
  this pass's effort budget - left raw rather than risk an
  under-verified "parked, confirmed correct" claim, following the same
  judgment call as `sub_8017AB0`/`sub_8018008` in `docs/status/actor.md`.
- **`sub_8016048`** - a smaller (~50-instruction) dispatcher on `self+8`
  and the current joystick input state, calling `sub_8017264` twice with
  a `0x7FFFFFFF`/`0x7FFFFFFF` sentinel pair; same reasoning as above,
  left raw, out of scope for this pass.

Both real-address boundaries stay accurate in `tools/report_units.py`'s
`UNITS` table (`0x080159F8` through `0x08016048`) even with `None` as
the unit's `base_object`, per that file's own convention for
high-confidence-but-still-raw stretches.
