# Issue #58 follow-up: 0x08030574-0x08031784

A follow-up pass on issue #58's boss-weapon effect state machine (see
[issue-58-0x08030334-actor.md](issue-58-0x08030334-actor.md) for the
original chunk writeup and the shared `self`/tracker-object background),
picking up the 6 units the previous pass left raw:
`sub_8030574`-`sub_80305F8`, `sub_8030648`, `sub_80306AC`-`sub_80309B4`,
`sub_8030D48`-`sub_80311C4`, `sub_8031378`, `sub_8031504`/`sub_8031604`.

All 15 functions in this range are now byte-exact (a full clean
`make compare` passes, `crashbandicootxs.gba: La suma coincide`), but
only 2 are real decompiled C - the rest hit genuine gcc-2.9 register-
allocation/scheduling gaps this compiler's own allocator can't be
coaxed past, and are tracked as parked `NAKED` transcriptions instead
(see docs/workflow.md's NAKED escape hatch and the "Critical policy"
note in this PR's description).

## Matched (2 of 15)

- **`sub_80305F8`** (`src/graphics/actor_part20d.c`) - an
  `InitActorPart`-based constructor forwarding all 4 of its own real
  arguments (the last stack-passed) to `InitActorPart`, then setting
  `self+0x54=2`, `self+0x50=&gStaticData_087E525C`, re-stashing `b`/`c`
  into `self+0x58`/`self+0x5c`, and a few fixed fields. The previous
  pass left this one raw over a "4-instruction scheduling permutation"
  in the stack-argument fetch; the fix was pinning the stack argument
  to `register s32 dReg asm("r0") = d;` *after* the other register
  pins (`bReg`/`cReg`/`health`) rather than alongside them - declaring
  it earlier makes this compiler fetch the stack slot ahead of the
  `r6`/`r8` parameter homes, opposite of the ROM's own order.
- **`sub_80306AC`** (`src/graphics/actor_part21c.c`) - advances
  `gUnknown_03001548` by its per-frame delta and, under a ceiling,
  resets the velocity group and fires the tracker object's state-2/
  table-index-0 transition, always ending with `sub_802A4F8()`. Needed
  two small idioms already established elsewhere in this project: a
  pair of "dummy" pointer locals (`s32 *p1558 = &gUnknown_03001558;
  s32 *p155C = &gUnknown_0300155C;`) declared in the order the ROM
  loads their *addresses*, even though the ROM *stores* to them in the
  opposite order - and a `register s32 two asm("r1") = 2;` deliberately
  scoped to occur *after* those two stores in the source, matching the
  ROM's own instruction order for when the constant gets materialized.

## Parked - NAKED transcription (13 of 15)

All of the following were fully understood (semantics documented in
each function's own doc comment and in `docs/status/actor.md`'s Parked
section) but hit a genuine compiler gap real effort couldn't close:

- **`sub_8030574`/`sub_8030648`** (`actor_part20b.c`/`actor_part21b.c`)
  - the keyframe-table AABB lookup/dispatch pair. Structurally
  identical to the already-parked `sub_802C208` (actor_part19.c,
  `gStaticData_0817A6B8` instead of `gStaticData_0817C2B8`) - same r7
  hazard: this agbcc build keeps the table's base address alive in
  `r7` for the whole function, but this compiler's own *unforced*
  allocator never reaches r7 for this shape (confirmed: a direct C
  translation compiles noticeably shorter code that never needs
  `r6`/`r7` to survive the `sub_803AD84` call at all).
- **`sub_8030734`** (`actor_part21d.c`) - `sub_80306AC`'s companion.
  A plain-C reconstruction (mirroring `sub_80306AC`'s successful
  pointer-pinning idioms) got every instruction byte-identical except
  one: `gUnknown_03001570 = *(s32 *)(table + 0x10);` compiles with the
  RHS's address loaded before the LHS's regardless of declaration
  order, opposite of the ROM's own build, and no C-level reordering
  (pre-declaring the destination pointer, splitting into a temporary)
  moved it. Given the size of the remaining chunk, this was
  transcribed NAKED instead of chased further.
- **`sub_8030834`** (`actor_part21e.c`) - a distance/speed-gated
  variant of `sub_8030734`'s spawn logic (`sub_802E674` instead of
  `sub_802E62C`), keeping the weapon table's phase pointer (`sb`) and
  raw phase value (`r8`) alive across a real `sub_803ADB4` call - the
  same many-high-register allocation difficulty documented throughout
  this project for `sub_8006600`/`sub_80372BC`/`sub_8038538`.
- **`sub_80309B4`** (`actor_part21f.c`) - a large 5-way weapon-kind
  projectile spawner dispatching on `gUnknown_0300153C` (thresholds
  `0xa`/`0x32`/`0x50`/`0x6e`/`0xaa`), each case clearing one BG
  palette-bank-1 slot then spawning 1-3 sub-projectiles via
  `sub_8000E1C`/`sub_802E420`. Shares base X/Y coordinates across the
  whole dispatch in `r7`/`sb`, and a per-kind Z-offset in `sl`/`r8` -
  the same register-pressure difficulty, compounded by five largely-
  duplicated dispatch arms that make a low-confidence partial C
  reconstruction especially risky.
- **`sub_8030D48`** (`actor_part23b.c`) - confirmed by
  `docs/rom_map.md` as "a rectangular BG-tilemap blit routine": streams
  16-bit tile-index pairs from `self`'s own data, biases each by
  `gUnknown_03001530`, and packs pairs into 16-bit VRAM writes over a
  32-tile-wide row. The nested row/column loop keeps its counters and
  cursor live in `sl`/`sb`/`r8`/`ip` simultaneously.
- **`sub_8030E08`** (`actor_part23c.c`) - the position-easing helper
  both `sub_8030734` and `sub_8030834` call: advances position
  accumulators, computes a per-axis signed distance from a keyframe-
  table-relative target, and nudges two "shake"/camera-offset
  accumulators (kept in `sb`/`r8`) toward it in discrete steps, with a
  final hard clamp. Same register-pressure family as the rest of this
  cluster.
- **`sub_8030F88`** (`actor_part23d.c`) - the tracker object's
  constructor: `mem_alloc`s the 0x1c-byte object, wires its event/part
  tables, registers it via `sub_803B0A8`, and fires the same state-0/
  table-index-0 transition idiom already matched in `sub_80306AC`. A
  first plain-C attempt (reusing that same idiom) compiled noticeably
  shorter/differently-structured code - this compiler proved several
  of the ROM's own reloads redundant and CSE'd them away. Given the
  ~50-instruction prologue's number of independent register-order
  choices, reproducing it register-for-register wasn't pursued further
  this pass (the same shape of gap already documented for
  `sub_802FA04`, actor_part45c.c).
- **`sub_8031040`** (`actor_part23e.c`) - a large "arm this weapon-
  kind instance" setup: resets ramp/velocity globals, fires a
  transition, seeds position accumulators from its own 3 arguments,
  looks up a per-kind keyframe-table record, and recomputes the BG2
  zoom scale/offset - keeping its three incoming position arguments
  and a per-kind table pointer in `r8`/`sb`/`sl` across several real
  calls (`sub_8029B2C`/`sub_803ADB4`/`sub_8029E34`).
- **`sub_80311C4`** (`actor_part23f.c`) - the per-frame "advance this
  weapon-kind instance" driver: fires a stride-4 trampoline, refreshes
  the palette-strip animation, advances the anim-frame accumulator
  once past its keyframe threshold, and shares `sub_8031040`'s exact
  accumulator-recompute tail. Hits the same "which operand's address
  loads first" gap as `sub_8030734` in its keyframe re-arm block.
- **`sub_8031378`** (`actor_part24b.c`) - an AABB overlap test against
  a keyframe-table box (`gStaticData_0817C3D8`), only run while the
  tracker's state global (`gUnknown_03001538`) is 2 or 3. Same 12-byte
  `{s16 x, y, z, sizeX, sizeY, sizeZ}` record shape and `sub_800014C`
  self-copy idiom as the already-parked `sub_802DD9C`/`sub_802D7B0`
  (actor_part75.c/actor_part74.c, docs/matching/issue-54-actor-d3a8.md)
  - transcribed for the identical register-pressure reasons.
- **`sub_8031504`** (`actor_part26b.c`) - DMA3-driven tile-cache clear
  + `sub_8031604` call, then (while the tracker's state is armed) a
  BG2CNT toggle, a keyframe-table box blit via `sub_8030D48`, and a
  palette-strip DMA fade gated on the tracker's state (5 or 4). This
  one is worth calling out specially: pinning `&gUnknown_03001538` to
  `r7` (matching the ROM's own register choice, which stays live
  across the `sub_8030D48`/`sub_80312C4` calls) doesn't just produce
  different bytes - this compiler decides r7 is "free" between the
  pin's two dereferences (nothing else in the C source still visibly
  needs it) and silently reuses it as scratch space for an unrelated
  `gUnknown_03001520 = 0;` assignment in between, then reloads from
  that now-clobbered register for the second dereference. That's a
  real correctness bug a byte-diff alone wouldn't necessarily catch on
  a differently-shaped example, not just a cosmetic mismatch - see
  docs/workflow.md step 3's warning about isolated compiles never
  being proof of a match. Abandoned immediately in favor of NAKED.
- **`sub_8031604`** (`actor_part26c.c`) - confirmed by
  `docs/rom_map.md` as one of the "procedurally-generated VRAM
  fill-level meter" twins (`sub_80336CC` is its still-raw sibling,
  outside this chunk): indexes `gStaticData_08167AD4`'s per-level
  table, sums heights into `gUnknown_03001530`, and DMAs the `0xFF -
  sum` fill level as packed 4-bit nibbles into VRAM. The inner
  nibble-packing loop holds `r8`/`sb`/`sl`/`ip` live simultaneously
  across its own internal branches.

## Verification

Every NAKED transcription in this pass was verified two ways before
being wired into `ldscript.txt`: first, per-function, by assembling
the exact original disassembly slice (from the still-then-raw
`asm/code_3_2_20_28568_c99c_*.s` files) alongside the isolated-compiled
NAKED `.c` file and comparing their `.text` section bytes directly
(`objcopy -O binary --only-section=.text` + `cmp`) - catching two real
transcription slips this pass (a duplicated store in `sub_8030734`'s
join point, and an off-by-one in a hand-extracted line range that
silently dropped a `thumb_func_start` macro and let one slice assemble
as 32-bit ARM instead of 16-bit Thumb). Second, the standard project-
wide verification: `rm -rf build && make NON_MATCHING=1 report` then
`rm -rf build crashbandicootxs.elf crashbandicootxs.gba
crashbandicootxs.map && make compare`, confirming `crashbandicootxs.gba:
La suma coincide` against the real ROM.

See [docs/status/actor.md](../status/actor.md) for the running
matched/parked list this entry feeds into. Issue #58 itself stays
open - `docs/matching/issue-58-0x08030334-actor.md`'s own "Left raw"
section (`sub_8030334`/`sub_803044C`, and a dozen more) still needs a
pass.
