# Issue #59 (+ #60/#61): 0x08031784-0x08033804 (actor)

Foundational scoping + Phase 1 pass on the raw gap between issue #58's
boss-weapon cluster write-up
([issue-58-0x08030574-actor.md](issue-58-0x08030574-actor.md), which
closes exactly at `0x08031784`) and issue #62's singleton cluster
([issue-62-0x08033804-actor.md](issue-62-0x08033804-actor.md), which

this range's original scoping estimate exactly - nothing has shrunk
since that estimate was made, contrary to the "cascading-suffix
filename" caveat that prompted this deeper look.

## The shared struct/convention

Confirmed on first read that this range is the **same** per-instance
boss-weapon/tracker "self" object family documented for issue #58/#62,
not a different system: state at `self+0x28`, table-index/"kind" at
`self+0xc`, an anim-frame halfword/byte pair at `self+0x10`/`self+0x12`,
an accumulator at `self+8`, a "part table" pointer at `self+0`, and an
event/trampoline table pointer at `self+0x50` - all present verbatim in
the very first functions read (`sub_80317E0`, `sub_8031858`,
`sub_80318B4`).

`docs/rom_map.md`'s existing whole-ROM reconnaissance passes (the
"boss/singleton" thread starting around "A shared 'type-byte event
dispatch' convention, and evidence of one large, complex actor object
(boss candidate)") had **already read and semantically characterized
most of the remaining 60 functions** in earlier research-only passes,
without decompiling them - this is a major head start for whoever picks
up Phase 2:

- `sub_8031B0C`/`sub_8031C0C`/`sub_8031D7C`/`sub_8031E80` - the shared
  "type-byte event dispatch" family (proximity or countdown trigger,
  always `PlaySfx(3, 0x100)`, then splits by a `self+0x30` type byte
  into `sub_8022EA8` or `sub_802F540` calls).
- `sub_8032480` - orbital motion via the shared trig table
  `gStaticData_0816A820` (3rd confirmed actor consumer).
- `sub_8032890` - a "spawn effect type N" homing/seek-toward-point twin
  of `sub_802C3E8`.
- `sub_8032C0C`/`sub_8032EA0` - open **a second RAM-struct family**,
  `gUnknown_030015B4`-`030015EC` (9 fields, ~56 bytes), a camera-
  follow/scroll-velocity smoothing computation; vtable-dispatched via a
  **third per-category table family** at `gStaticData_0817C4xx`
  (distinct from the entity/actor-category vtables).
- `sub_8033264` - the animation-system-wired constructor/init step for
  that same `gUnknown_030015Bx` object (calls `GetAnimFrameBaseOffset`).
- `sub_8033048`/`sub_80330FC`/`sub_8033470`/`sub_8033550`/`sub_8033604`
  - a **second unique/singleton object**'s patrol driver, tile-consumer,
  per-frame animate+project+tile-stream update, and BG2 affine-matrix
  committer - closely-parallel machinery to the boss cluster, on a
  completely separate global cluster.
- `sub_80331BC` - **the missing constructor for the whole singleton
  system**: allocates the object, stores it into the global pointer
  `gUnknown_030015AC` everything else in this thread reads, and fires
  the per-frame update driver once. A strong anchor function for
  whoever continues Phase 2 - see `docs/rom_map.md`'s "`sub_80331BC`
  closes a long-open question" section for the full account.
- `sub_80336CC` - the P2-side VRAM fill-level meter, a near-identical
  twin of the already-matched `sub_8031604` (issue #58,
  `actor_part26c.c`).

The remainder (`sub_8031D04`, `sub_8031F78`-`sub_80321FC`,
`sub_8032274`-`sub_80323F4`, `sub_8032440`-`sub_803290C` minus the
named ones above, `sub_8032910`-`sub_8032AF8`, `sub_8032B6C`,
`sub_80337E4`-`nullsub_35`) are still genuinely unread at the
individual-function level - plausibly more members of the "spawn
effect type N" family (≥9 siblings already confirmed elsewhere,
`sub_802E504`-`sub_802E6CC`) and small field accessors on the two
struct families above, but not confirmed. `docs/rom_map.md` is the
first stop for anyone picking this up - search it for the specific
`sub_80xxxxx` name before re-reading the raw bytes from scratch.

## What this pass closed (Phase 1: 15 of 75 functions, `0x08031784`-`0x08031A6C`)

New file: `src/graphics/actor_part125.c` (checked both the `src/graphics/`
directory listing *and* every `actor_part<N>.o` reference already inside
`ldscript.txt` for the highest in-use number before picking `125` -
`actor_part110` through `124` were already reserved by earlier work
despite not each having a same-numbered `.c` file visible from a naive
`ls actor_part10*.c`/`actor_part9*.c` glob, which is exactly the
collision this project's `docs/matching.md`/session memory warns about;
see "A costly near-miss" below).

**Matched (9 of 15, real C):**

- `sub_8031784` - tracker "ready" check: while inactive
  (`gUnknown_03001538 == 0`) reports not-ready; otherwise scales the
  countdown `gUnknown_0300156C` through `sub_803ADB4` against the small
  weapon-kind table's first field. Needed the countdown value pinned to
  `r4` and read once (`register s32 countdown asm("r4")`) so both the
  multiply and the later `> 0` check reuse the same register the ROM
  does, instead of gcc reloading it from the cached address a second
  time.
- `sub_80317C4` - tracker destructor (`mem_free(gUnknown_03001534)`),
  `sub_8030F88`'s (issue #58) counterpart.
- `nullsub_30`/`nullsub_31`/`nullsub_32` - no-op stubs.
- `sub_8031850` - trivial `self+0x58` clearing setter.
- `sub_80318B4` - full state/accumulator/anim-frame reset idiom (state
  = 1, `self+0x58`/`0x60`/`0x44`/`0xc`/`8` cleared, anim frame re-synced
  from `self`'s own part table) - same shape as the established
  `sub_80306AC` reset block (issue #58, `actor_part21c.c`). The `one`
  register pin (`self+0x28 = 1`) had to move into its own nested block
  *after* the two zero-stores that precede it in the ROM's own
  instruction order, not declared alongside `zero` up front - otherwise
  gcc hoists its materialization ahead of those stores.
- `sub_8031920` - `InitActorPart`-based constructor, same shape as the
  already-matched `sub_80305F8` (issue #58, `actor_part20d.c`) but with
  a 6th argument (stashed into `self+0x58`) instead of a second stash of
  `c`.
- `sub_8031A64` - trivial `self+0x5c` byte getter. Needed a trailing
  `asm(".align 2, 0")` for the lone-function-at-end-of-translation-unit
  padding gap already documented for `sub_80306A4`/`sub_8033CF0`.

**Parked - NAKED transcription (6 of 15, byte-correct but not counted
as matched):**

- `sub_80317E0` - proximity-gated event trigger (syncs via
  `sub_802A980`, camera-relative bound check, flushes a pending
  trampoline call, draws a text popup or falls back to `sub_8031A08`).
  This compiler doesn't reach for `r4` as the whole-function `self` pin
  the ROM uses without also perturbing the branch layout.
- `sub_8031858` - health/damage-countdown death transition, same shape
  as the boss cluster's `sub_8030530`. The death-byte `1`/`0` constants
  need to stay live and shared across both the early-flush branch and
  the later state-transition block in a way register pins alone
  couldn't reproduce without changing the branch shape.
- `sub_80318D0`/`sub_8031954`/`sub_80319A0` - three instances of a
  shared anim-frame-advance-and-clamp idiom (the first stashes 3
  incoming args into `self+0x1c`/`0x20`/`0x24`; the third adds an
  oscillation drive on `self+0x20`/`0x60`). This compiler always
  schedules the `#4`/`#6` `ldrsh` constant loads one instruction earlier
  than the ROM's own build - a genuine scheduling gap, not a register
  choice.
- `sub_8031A08` - keyframe-table-relative text popup draw, indexing
  `gStaticData_0817C414` by `self+0x28`. Resists a byte-exact
  reproduction of the ROM's specific `r7`-as-table-base-pin choice.

All 15 verified via the mandatory full pipeline: `rm -rf build && make
NON_MATCHING=1 report` (no warnings for `actor_part125.c`), then
`rm -rf build crashbandicootxs.elf crashbandicootxs.gba
crashbandicootxs.map && make compare` confirming `crashbandicootxs.gba:
La suma coincide`.

## A costly near-miss (filename collision, caught before commit)

While picking this pass's new filename, an `ls src/graphics/actor_part10*.c`/
`actor_part9*.c` glob check missed `actor_part110.c`-`actor_part124.c`
entirely - `actor_part10*` only matches `actor_part100`-`actor_part109`
(and `actor_part10` itself), never `actor_part110`+, since `11` isn't a
prefix of `10`. This session's first draft of this pass's file was
therefore written to `src/graphics/actor_part110.c`, silently
**overwriting** an already-matched, unrelated file (a large,
fully-documented investigation into `sub_800A178`/`sub_800A420`'s
collision-probe orchestration, GitHub issue #9/#10 - see that file's own
header comment) that ldscript.txt already referenced from a completely
different ROM address (~`0x8009xxx`-`0x800Axxx`). The mistake was caught
immediately via `git diff --stat` before any commit (804 lines deleted,
453 inserted) and fully reverted with `git checkout ef0ecde --
src/graphics/actor_part110.c`; the new content was moved to
`actor_part125.c` instead, and `ldscript.txt`'s corresponding line was
retargeted. **The correct check going forward is the higher of (a) the
highest `actor_part<N>.c` on disk sorted numerically, not
lexicographically/glob-matched, and (b) the highest `actor_part<N>.o`
referenced anywhere in `ldscript.txt`** - the two can disagree, as they
did here, whenever a chunk earlier in this session claimed a number
without yet materializing every file `ldscript.txt` reserves a slot for.
