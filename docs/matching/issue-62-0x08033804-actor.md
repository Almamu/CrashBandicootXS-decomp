# Issue #62: 0x08033804-0x08033EF4 (actor)

25-function `decomp-chunk` covering the `gHovercraft` singleton
system's accessor/state-machine cluster - see `docs/rom_map.md`,
"Follow-up reads `HovercraftCannonStateFire`'s helper cluster and `UpdateHovercraft`" and
"`CreateHovercraft` closes a long-open question: the missing singleton
constructor" for the prior research this pass builds on. The functions
that take an explicit `self` pointer (`DamageHovercraftCannon`, `UpdateHovercraftCannon`,
`CreateHovercraftCannon`, `HovercraftCannonStateDestroyed`, `HovercraftCannonStateWait`, `RunHovercraftCannonState`,
`IsHovercraftCannonUnshootable`, `HovercraftLauncherStateLaunch`, `DamageHovercraftLauncher`, `UpdateHovercraftLauncher`,
`HovercraftCannonStateFire`) share the same per-instance "self" object layout already
documented for the boss-weapon cluster (`actor_part20.c`-
`actor_part26.c`, issue #58): state at `self+0x28`, table-index/"kind"
at `self+0xc`, an anim-frame halfword/byte pair at `self+0x10`/
`self+0x12`, an accumulator at `self+8`, a "part table" pointer at
`self+0`, and an event/trampoline table pointer at `self+0x50` - plus a
health-like countdown at `self+0x54` and a death/"dead" byte flag at
`self+0x6c` specific to this cluster.

The raw source file `asm/code_3_2_20_28568_c99c_31784.s` has been split
around each matched/parked function, following this project's "cut at
the boundary" convention - new fragments are named by the lower 5 hex
digits of their first function's address
(`..._339dc.s`, `..._33b44.s`, `..._33c84.s`, `..._33cf8.s`,
`..._33e80.s`, and the tail continuation `..._33ef4.s`).

## Matched (20 of 25 functions)

- **`StartHovercraftHitFlash`** (`src/graphics/actor_part28.c`) - one-shot latch
  arming `gHovercraftHitFlashOn`/`gHovercraftHitFlashTimer` together the first
  time both are still clear.
- **`SetHovercraftFlashColor`** (`src/graphics/actor_part28.c`) - speed-override
  toggle for a P1/P2-mirrored object pair (`gFlashBgPalette`/
  `gFlashObjPalette`, a "genuinely new global family" per
  `docs/rom_map.md`). Needed register pins matching the ROM's exact
  choices in each branch (`r0` in the "flag set" branch, `r2` in the
  "flag clear" branch, `val` itself pinned to `r1` for the whole
  function) - without them this compiler's own register choice made
  both branches' tails byte-identical and merged them via cross-jump
  optimization, which the ROM's build didn't do.
- **`GetHovercraftPartsLeft`/`GetHovercraftAttack`/`GetHovercraftState`/`GetHovercraftLevel`/
  `GetHovercraftZ`/`GetHovercraftY`/`GetHovercraftX`** (`src/graphics/actor_part28.c`)
  - trivial one-line getters for the singleton's fields.
- **`LoseHovercraftPart`** (`src/graphics/actor_part28.c`) - the singleton's
  death/reset transition: plays a sound, decrements the lifetime
  counter `gHovercraftPartsLeft`, and at zero fires `SetHovercraftState(5, 0)`.
- **`SetHovercraftState`/`HovercraftStateApproach`** (`src/graphics/actor_part28.c`) -
  the singleton's state-transition/anim-frame-reset setters, the same
  idiom as the boss cluster's `DamageAirshipFireball`/`AirshipStateFall`. Needed the
  established `register ... asm("rN")`-pinned reset-idiom blocks
  throughout, plus one new wrinkle in `HovercraftStateApproach`: two back-to-back
  zero-stores to different globals (`gHovercraftVelY`/
  `gHovercraftVelX`) needed their *addresses* pinned to specific
  registers (`r0`/`r1`) matching the ROM's load order, not just the
  shared zero value.
- **`nullsub_36`/`nullsub_37`** (`src/graphics/actor_part28.c`) -
  no-op stubs.
- **`DamageHovercraftCannon`** (`src/graphics/actor_part30.c`) - applies damage to
  `self+0x54`, transitioning to the death state/anim once it drops to
  zero. The death block needed an outer `zero` pinned to `r4` (reused
  for two stores) and an inner `zero2` pinned to `r1` (a single store),
  the same two-level-zero idiom already documented for the boss
  cluster's `DamageAirshipFireball`.
- **`CreateHovercraftCannon`** (`src/graphics/actor_part32.c`) - `InitActorPart`-
  based constructor. The real gap here: the ROM keeps constructor
  argument `c` in the high register `r8` for the whole function (with
  the accompanying `mov r6,r8`/`push {r6}` .. `pop {r3}`/`mov r8,r3`
  callee-save relay), even though only three simultaneous values
  (`self`, `b`, `c`) are live across the `InitActorPart` call and three
  low registers (`r4`-`r6`) would easily suffice - this compiler's own
  allocator always prefers the low registers when they fit, so `c` had
  to be explicitly pinned to `r8` to reproduce the ROM's choice. Fixing
  this also resolved a 12-byte size regression that had shifted every
  function after it in the ROM (see "A note on isolated-compile
  confidence" below).
- **`HovercraftCannonStateDestroyed`** (`src/graphics/actor_part32.c`) - plays a fixed
  sound cue, then conditionally fires an event-table trampoline. The
  16-bit table offset load needed the constant `8` pinned into `r2` and
  used as a *register*-offset `ldrsh` (`ldrsh r0,[r1,r2]`) rather than
  the immediate-offset `ldrh`-plus-manual-sign-extend this compiler
  defaults to for a compile-time-constant offset - Thumb1 `ldrsh` has
  no immediate-offset encoding at all, so the ROM's build must have
  materialized the offset into a register too.
- **`HovercraftCannonStateWait`** (`src/graphics/actor_part32.c`) - position sync
  from the singleton plus a state-1/table-index-1 transition. Same
  "value pinned/scheduled to match ROM's interleaved zero/one stores"
  gap as `DamageHovercraftLauncher` below.
- **`IsHovercraftCannonUnshootable`** (`src/graphics/actor_part34.c`) - trivial
  `self+0x6c` death-flag getter. Needed a trailing `asm(".align 2, 0")`
  - same lone-6-byte-function-at-end-of-translation-unit padding gap
  documented for `IsAirshipFireballUnshootable` in issue #58's write-up.
- **`DamageHovercraftLauncher`** (`src/graphics/actor_part36.c`) - `DamageHovercraftCannon`'s
  state-1-gated twin. Two distinct register-choreography gaps: the
  death-flag store reuses the just-checked `state` variable (still
  holding `1`) instead of a fresh literal, matching the ROM's literal
  register reuse; and the `self+0x28`/`self+0xc` stores need their
  source values (`2` and `3`) pinned to `r0`/`r1` and computed together
  *before* either store, not interleaved with the unrelated `self+0x44`
  zero-store the way a natural top-to-bottom C translation produces.
## Parked (2 of 25 functions, `NON_MATCHING`)

- **`HovercraftCannonStateFire`** (`asm/code_3_2_20_28568_c99c_31784_339dc.s`, C in
  `src/graphics/actor_part29.c`) - a proximity-triggered effect/hazard
  detector: syncs `self`'s position to the singleton's, measures
  distance to the player, and if in range spawns a pair of effects.
  Semantics fully understood and every load/store, branch and call
  confirmed correct; the ROM keeps `self+0x64`'s cached "slot" value in
  the `sb`/`r9` high register for the whole function (needing a second
  high-register relay pair, `mov r7,sb`/`mov r6,r8`/`push {r6,r7}`, at
  entry), while explicit `r9` and `ip`/`r8` pins here get every other
  register placement to match except one 16-bit-constant materialization
  early in the function (`gHovercraftY + 0x3000`, `self+0x20`)
  where this compiler picks `r1` for the intermediate `0x3000` load and
  this compiler's own scratch-register choice for the immediate can't
  be steered to the ROM's `r2` without breaking the surrounding
  register pins.
- **`HovercraftLauncherStateLaunch`** (`asm/code_3_2_20_28568_c99c_31784_33cf8.s`, C in
  `src/graphics/actor_part35.c`) - `HovercraftCannonStateFire`'s sibling: the same
  proximity/spawn-detector shape, picking one of three spawn "kinds"
  via `RandRange(3)`. Semantics fully understood and every branch and
  call confirmed correct; the ROM keeps `self` in `r5`, the player
  pointer in `r6`, and the `self+0x64` "slot" cache in `r7` for the
  whole function (`push {r4,r5,r6,r7,lr}`, no high registers needed at
  all here, unlike `HovercraftCannonStateFire`). Explicitly pinning the slot cache to
  `r7` compiles, but an isolated test confirmed this specific agbcc
  build never emits the matching push/pop for a plain low-register
  (`r0`-`r7`) `register` variable used across a call when no *other*
  high register is also live in the same function - it silently drops
  the callee-save, which would corrupt the caller's `r7` if shipped.
  (`HovercraftCannonStateFire` avoids this because it already needs `r8`/`sb`, and
  the resulting `mov r7,sb`/`push {r6,r7}` relay happens to cover `r7`
  as a side effect; `HovercraftLauncherStateLaunch` has no such second high register to
  piggyback on.) Reverted to a safe, unpinned - and therefore
  non-matching but correct - reconstruction rather than ship code that
  silently clobbers a caller register.

## NAKED transcription (byte-correct, not counted as matched)

- **`UpdateHovercraftCannon`** (`src/graphics/actor_part31.c`) - position-update-
  then-draw helper via a `gHovercraftCannonStateFuncs` stride-8 trampoline
  table, same shape as `RunPolarPlayerState` (issue #52).
- **`RunHovercraftCannonState`** (`src/graphics/actor_part33.c`) - `UpdateHovercraftCannon`'s
  predicate twin (same stride-8 table, returns a bool instead of
  tail-calling `UpdateActor`).
- **`UpdateHovercraftLauncher`** (`src/graphics/actor_part37.c`) - `UpdateHovercraftCannon`'s
  twin using the second stride-8 table (`gHovercraftLauncherStateFuncs`).

Revisiting the "record pointer" framing above: the real blocker turned
out to be that the ROM keeps `gHovercraftCannonStateFuncs`/
`gHovercraftLauncherStateFuncs`'s base address alive in `r7` for the whole
function - this project's confirmed categorical gcc-2.9 r7-pin bug (an
explicit `register T x asm("r7")` compiles correct instructions but
never makes it into the prologue/epilogue `push`/`pop` list, and this
compiler's own unforced allocator never reaches r7 here either) - not
a fixable CSE/scheduling gap. All three are transcribed as NAKED asm
(every instruction byte-verified against the ROM disassembly - see
docs/matching/issue-52-0x0802bed8-actor.md's `RunPolarPlayerState` entry for
the full account), so the built ROM is byte-identical at these
addresses, but per this project's current tracking policy a NAKED
transcription of a substantial function doesn't count as "matched" -
`tools/report_units.py` keeps these three addresses' `base_object` as
`None`. `HovercraftLauncherStateLaunch` above hits the *other* r7-hazard variant (a
plain low-register pin dropped entirely, not even a wrong-but-present
one) and remains parked (not transcribed).

## A note on isolated-compile confidence

`CreateHovercraftCannon`'s missing `r8` pin (see above) produced code 12 bytes
*shorter* than the ROM - undetectable from an isolated per-function
compile's instruction-for-instruction read alone, since the isolated
compile still "looked right" locally. It only surfaced once the whole
chunk was cut into its real `.c`/`.s` files and linked: every function
address after `CreateHovercraftCannon` in the map file was off by exactly -12
bytes from its expected ROM address, pointing straight at the one
function whose size had actually changed. This is exactly the
map-file address-shift diagnostic `docs/workflow.md` describes, and is
recorded here as a second concrete instance (alongside the `CullPartList`/
`CollidePartsOfClass` and `RemoveCrateListAt`/`LinkCrateInGrid` pairs already documented)
of an isolated compile looking correct while still hiding a real gap -
several more one-instruction-order gaps in this chunk
(`HovercraftStateApproach`'s zero-store address order, `HovercraftCannonStateDestroyed`'s `ldrsh`
addressing mode, `HovercraftCannonStateWait`'s and `DamageHovercraftLauncher`'s interleaved
zero/one stores) were only caught by this same full-link byte-diff
process, not by re-reading the isolated compile output more carefully.

See [docs/status/actor.md](../status/actor.md) for the running
matched/parked list this entry feeds into.

## Later pass: member-pointer dispatch

A later pass promoted `UpdateHovercraftCannon` (`actor_part31.c`), `RunHovercraftCannonState` (`actor_part33.c`) and `UpdateHovercraftLauncher` (`actor_part37.c`) from NAKED to real C. The "r7 table-base"
shape was gcc 2.x's pointer-to-member-function call
`(this->*table[this->state])()`, which `ACTOR_PMF_CALL` in
`include/actor_self.h` reproduces with no register pins. See
[pmf-dispatch-retry.md](pmf-dispatch-retry.md).

## Later pass: strag2 retry

`HovercraftCannonStateFire` and `HovercraftLauncherStateLaunch`, the two functions parked above, are
now matched as real C. Their raw `asm/code_3_2_20_28568_c99c_31784_339dc.s`
and `..._33cf8.s` files and `ldscript.txt` lines are deleted. The C
objects (`actor_part29.o`, `actor_part35.o`) were already linked in ROM
order. Both compile to the same bytes under agbcc and old_agbcc. The
parked notes blamed register allocation, but the source shape was wrong:

- **The divisions are real `/`.** They go through the ROM's own
  `__divsi3`. As a libcall the
  division doesn't clobber memory, so `self+0x24` stays in `r6` across
  both divides and feeds `SpawnJetpackCannonball` without a reload. That is where
  the old draft's missing `sb`/`ip` values came from. `HovercraftCannonStateFire`'s
  divisor is also `-0x1AA`, not the old draft's `-0xAA`.
- **One store for the new cooldown.** The table value (either arm) and
  `slot - 1` all go through a `next` local to one `store:` label. That
  gives the ROM's shared `str r0, [r5, #0x64]` and keeps `slot` in
  `sb`/`r7` untouched.
- **The counter.** `count = self->0x68 + 1` stored and then compared
  keeps `count` in `r4` across the `GetHovercraftAttack` call.
- **Order of the `dx`/`dy` statements.** Compute `rawDx`, then `dx`,
  then `rawDy`, then `dy`, and take `|dx|` before `|dy|`.
- **Zero constants.** The reset block's byte zero is a `u8` from an
  `asm("" : "=r"(zero) : "0"(0))` escape, set after loading the
  animation halfword. `HovercraftLauncherStateLaunch` also materializes its `0` and `2`
  that way; its `2` needs `asm volatile` so it isn't sunk to its store.

No register pins were needed. `HovercraftLauncherStateLaunch`'s `r7` for the slot comes
from the allocator alone.
