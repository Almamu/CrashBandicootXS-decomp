# Issue #67: `0x08038538`-`0x08039658` (audio, second pass)

Continues PR #198's first pass at this chunk (6/25 matched - see
`docs/matching.md`'s `0x08038538`-`0x08039658` entry, now frozen, for
that pass's write-up and the full "left raw" catalog it produced). This
pass adds 2 more matches for 8/25 total; the remaining 17 are left raw
for the reasons already documented in `docs/matching.md` plus one newly
confirmed case below.

## Matched this pass

- **`src/audio/gax_fatal_error.c`** (`sub_80392E0`, ROM `0x080392E0`) -
  GAX2's fatal-error screen. Disables Timer0-3 direct-sound-output
  ticking via `sub_80391E8` (still raw - see below), zeroes the whole
  64KB of BG VRAM, decompresses a font tileset from a fixed IWRAM
  scratch address (`gUnknown_030008D0`, per `sym_iwram.txt`) via the
  HuffUnComp SWI wrapper (`sub_80392C4`, already matched as `NAKED` asm
  in `gax_swi.c`) into BG char block 1, explicitly blanks that block's
  first tile (the "space" glyph, 32 bytes = 16 halfwords), pokes four
  raw tilemap addresses (`0x060044B8`/`0x060044C8`/`0x060044FC` - not
  screen-block-aligned, so kept as raw literals rather than
  `BG_SCREEN_ADDR(n)`), draws a fixed header string plus the caller's
  two message-line arguments via `sub_8039214` (still raw - a
  word-wrap text/console-tile renderer), resets the BG0/backdrop
  palette to black-on-white, enables BG0 only, and spins forever -
  nothing ever returns from this function. Matched with a completely
  straightforward one-to-one C reconstruction - no register-pinning or
  compiler-quirk workarounds needed, every hardware-register write and
  call landed in the ROM's exact instruction order and registers on the
  first isolated-compile attempt.
- **`src/audio/gax_sound_handler_info.c`** (`sub_803943C`, ROM
  `0x0803943C`) - the GAX2_SoundHandler "Info" type's play_fn (ROM
  `0x0803943D` per `docs/audio.md`'s per-type function-pointer table),
  joining the other three "Info" functions (`sub_80393D0`/
  `sub_80393FC`/`nullsub_39`) already matched in this file. A per-tick
  repeat/retrigger scheduler: bails out immediately (still returning 0)
  unless this is a new channel (`self->0xc != chanArg`) and the handler
  is armed (`self->0x1a != 0`). When armed and
  `self->0x18(byte) != 0 && self->0x1c(byte) == 0`, it advances a
  shared 8.8-style rate/counter pair (`self->0x16`, `self->0x18`) -
  either reloading `self->0x16` from `self->0->0x18`'s table (a still-
  unmodeled pointer chain, same situation as `sub_8038F94`/
  `sub_80393D0`) when a one-shot retrigger flag (`self->0x22`) is set,
  or simply incrementing it - then folds `self->0x18`'s high byte back
  into its low byte if present, decrements `self->0x1c` from
  `self->0x18`'s low byte, and compares `self->0x16` against two more
  thresholds from the same table (`self->0->0x18 +2/+4/+6`) to arm/
  disarm "loop point hit" flags at `self->0x1e`/`self->0x21` and reset
  `self->0x14`. The other branch (`self->0x18==0` or `self->0x1c!=0`)
  just decrements `self->0x1c` and clears `self->0x1d`. Finally records
  the new `chanArg` into `self->0xc` (and `self->0x10`, if still unset)
  and decrements `self->0x1b` if armed.

  This one needed real iteration to land byte-exact - three separate
  compiler-codegen gotchas, each confirmed by isolating the diff to a
  specific byte range and comparing raw bytes directly against
  `baserom.gba` (not just an isolated-compile "looks right"):
  1. The `self->0x1c==0` "known zero" copy must only be materialized
     *inside* the `self->0x18(byte)!=0` branch (a nested `if`, not a
     single `&&` condition) - the ROM only computes this copy after
     confirming the outer condition, then reuses that same register
     both for the second comparison and, later, as the literal 0
     stored into `self->0x22`. Writing it as a flat `&&` moved the copy
     instruction earlier than the ROM has it.
  2. The two `self->0x16`/`self->0x14` reads compared against the
     `self->0->0x18` table are 16-bit *signed* loads at a non-immediate
     offset (`0x16`/`0x14`) - Thumb's `ldrsh` has no immediate-offset
     encoding, only register-offset, so gcc must first materialize the
     offset into a scratch register. Left to its own devices gcc picks
     a different register pairing than the ROM (and inserts a redundant
     sign-extend mask pass when the value is pinned to force the ROM's
     registers "the normal way"). Transcribing the exact two-instruction
     sequence (`movs r0,#0x16` / `ldrsh r1,[r3,r0]`) as a tiny raw `asm`
     block per read, with the C-level result captured into a
     register-pinned `s32`, was the only way found to force the ROM's
     exact register choice without disturbing anything around it.
  3. The `self->0x1c`/`self->0x1d` "not retriggering" fallback path
     needs its decrement (`b1c - 1`) computed into a *fresh* register
     (pinned to `r0`) rather than modified in place on the register
     `b1c` was already loaded into (`r1`) - gcc's default choice reuses
     `r1` in place (`subs r1,r1,#1`), one instruction shorter than the
     ROM's separate `subs r0,r1,#1` / `movs r1,#0` pair, since the ROM
     keeps the old `b1c` value's register free for the following
     `movs r1,#0`.

  The object these two functions operate on isn't confidently modeled
  yet (same situation as `sub_80381FC`'s constructor in
  `sound_object_init.c`) - kept as raw offsets throughout rather than a
  guessed struct.

## Left raw, not (further) attempted this pass

Everything documented as left raw in `docs/matching.md`'s
`0x08038538`-`0x08039658` entry remains raw - `sub_8038538`/
`sub_8038A1C`/`sub_8038B68` (many-register `r8`/`sb`/`sl` gcc-2.9
allocation ceiling), `sub_8038FD0`/`sub_8039064`/`sub_80390F8`
(confirmed loop-allocation ceiling), `sub_8039198`/`sub_80391E8`
(hardware-register NOP-delay compiler quirk), `sub_8039214`,
`sub_8039518`, `sub_80395A4` - real attempts were made on a few of
these this pass and each is worth recording precisely:

- **`sub_8038E74`** (voice-stealing mixer allocator, characterized in
  prose by `docs/audio.md`) - its prologue (`push {r4-r7,lr}; mov
  r7,r8; push {r7}; mov r8,r0`) is the same many-register shape already
  flagged for the `sub_8038538` cluster; not attempted further given
  that established difficulty.
- **`sub_8038C88`/`sub_8038DC0`** - more GAX2 mixer-tick internals
  (`sub_8038DC0` a priority-scan loop very similar in shape to
  `sub_8038E74`'s inner loop). Read in full to understand what they do,
  but not attempted as a C reconstruction this pass - deprioritized in
  favor of landing the two matches above solidly, given the effort the
  play_fn match above already took. A reasonable next target for
  whoever picks this up: both avoid `r8`/`sb`/`sl` in their own
  prologues, so they may not hit the same ceiling as their neighbors.
- **`sub_8039518`** (Channel type's init_fn) - fully understood (same
  field-reset shape as `sub_803A104`'s per-channel voice constructor in
  `gax_channel_init.c`, plus a loop calling `sub_803AD7C` over a
  children array and a call into the still-raw 64-bit division helper
  `sub_8037A7C`) and an isolated-compile reconstruction was built and
  iterated close to matching (register-pinning got the whole rest of
  the function byte-identical), but one call site resists every C form
  tried: `sub_8037A7C(0, 1, chanArg, 0)`'s first two arguments (`0`,
  `1`) are loaded via `ldr rX,=0x00000000` / `ldr rX,=0x00000001` (four
  extra bytes of literal-pool data plus two 2-byte `ldr` instructions)
  in the ROM, instead of the `movs rX,#0`/`movs rX,#1` immediate-move
  form gcc always chooses for a plain integer literal or local variable
  in this position - confirmed with several isolated minimal repros
  (literal argument, hex-literal argument, pointer-typed argument, a
  local variable initialized before the call) that all still compile to
  `movs`. Whatever source-level construct makes gcc pool-load a
  small integer constant here isn't identified yet. Left raw rather
  than guessed at further - a good target for a future pass with more
  budget to spend hunting this specific quirk (it may be the same
  family of issue as the "hex-asm" literal-pool quirks already
  documented elsewhere in `docs/matching.md`, worth cross-referencing).
- **`sub_8039214`** (word-wrap text/console-tile renderer, called by
  the newly-matched `sub_80392E0` above) - fully read and understood
  (a per-character loop that computes a VRAM tilemap destination
  address from column/row arguments, does word-wrap lookahead up to 29
  columns before wrapping to the next tile row, then remaps a handful
  of ASCII punctuation characters and clamps the rest into a small
  glyph-index range before writing each remapped tile index) but not
  attempted as a C reconstruction - genuinely complex control flow
  (nested lookahead loop with two different register-reuse patterns for
  the same "current character" value) that would need the same kind of
  careful byte-level iteration `sub_803943C` above required, and was
  deprioritized this pass in favor of landing solid matches elsewhere.
- **`sub_80395A4`**/**`sub_8039658`** (Channel type's play_fn and its
  callee) - `sub_80395A4` itself avoids `r8`/`sb`, but its direct
  callee `sub_8039658` uses `mov r7,sb; mov r6,r8` in its own prologue
  - the same many-register shape. Not attempted this pass.
