# `0x08039818`-`0x0803A944` (audio, issue #68)

Six functions matched out of the 21-function chunk GitHub issue #68 covers
(`0x08039658`-`0x0803A944`, deep in the Shin'en GAX2 sound engine's own
code - see [`docs/audio.md`](../audio.md)). This range picks up right
after issue #67's pass ended (`sub_80395A4` onward) and runs up to the
BIOS `svc` wrapper stubs docs/audio.md already documents as the true end
of the engine. As with #66/#67, most of this range hits the same
many-register (`r8`/`sb`/`sl`) gcc-2.9 allocation ceiling already
catalogued for `sub_8006600`/`sub_8038538` - this pass only took the
handful of functions that don't touch that many live values at once.

## Matched

- **`src/audio/gax_channel_note_cut.c`** (`sub_8039818`) - dispatches a
  small per-channel command value against a voice object: `cmd == 1` is
  a note-cut case (arms a fixed note-off envelope only when the bound
  instrument's `+0x7d` byte is the `0xff` sentinel, then sets a
  "stopped" flag at `+0x22`); `cmd > 1` derives a pattern-note-looking
  value into `+0x26` instead and clears the flag again. Voice object
  shape isn't modeled yet - every field stays a raw offset, matching the
  neighboring GAX2 internals already in this directory.
  - The `cmd > 1` tail (`(cmd - 2) << 5`) needed its own instruction-order
    gotcha: with `cmd` pinned to `r3` (required for the two `cmp r3, #1`
    comparisons to reuse one register, matching the ROM's `bls`/`bne`
    pair), computing `(cmd - 2) << 5` straight from the pinned variable
    keeps reusing `r3` for the whole expression - the ROM instead moves
    the *subtraction's result* into a fresh register (`r0`) via a single
    `subs r0, r3, #2` (Thumb's 3-operand immediate-subtract form, Rd !=
    Rs). Assigning a *second* value to `r3` first (a plain copy) and
    subtracting from that gets CSE'd away since it's the same value -
    only pinning a fresh register to the **subtraction expression itself**
    (`register u32 tmp asm("r0") = v - 2;`) reproduces the single-
    instruction `subs r0, r3, #2` byte-for-byte.
  - Also needed `cmd` as `u32`, not `s32`: the ROM's `cmp r3, #1` / `bls`
    (unsigned "less-or-equal") for the `cmd > 1` gate compiles from a
    signed comparison as `ble` instead - a different condition-code
    nibble in the branch encoding, 2 wrong bytes that don't show up
    without a full linked comparison (see the general note on isolated
    compiles below).
- **`src/audio/gax_channel_effect_table.c`** (`sub_8039FFC`) - per-tick
  vibrato/tremolo-style effect: ticks a delay counter (`+0x23`) down
  once per call, and once it expires derives a new 0-0x3f phase index
  (`+0x3a`) from the bound instrument's `+0xa` step value, then looks
  the phase up in a signed table (`gStaticData_085A9EAC`) and scales the
  result by the instrument's `+9` byte (`>> 8`, standard Q8 multiply-down)
  into `+0x2e`.
  - The final `tableVal * instrument[9]` combination only reproduced the
    ROM's `ldrsb`-based table read (rather than a plain `ldrb` + two
    manual sign-extend shifts) once the second operand was inlined
    directly into the multiply expression instead of being split into
    its own named local - a named `u8 *inst2 = ...;` declared just
    before the multiply got hoisted *earlier* by the scheduler (ahead of
    the table lookup it doesn't depend on), landing in the wrong
    register entirely. Folding it into
    `result = (tableVal * (*(u8 **)(p + 0x3c))[9]) >> 8;` keeps the two
    loads in the ROM's actual order.
- **`src/audio/gax_channel_init.c`** (`sub_803A104`) - per-channel voice
  object constructor: clears the accumulator/instrument-pointer fields,
  arms the `0x8AD0` "no note" sentinel envelope, sets a default priority
  (`0xff`) and portamento speed (`-1`, i.e. "off"), then picks `+0x52`
  from a single flag byte read off `gUnknown_03001630` itself (not
  through any documented field - `+0x42` past the end of the currently-
  modeled `struct GaxPlayerState`, kept as a raw offset).
  - Needed the same two-named-zero-registers split already documented
    for `sub_80393D0` (`gax_sound_handler_info.c`): one zero temp for the
    first run of stores (reused freely since nothing else needs that
    register yet), a *second*, explicitly `asm("r1")`-pinned zero for the
    later run - otherwise gcc's CSE collapses the ROM's two separate
    `movs r0,#0`/`movs r1,#0` into one.
  - The `-1` store (`rsbs r0, r0, #0` after `movs r0, #1` in the ROM,
    i.e. negate-via-immediate-1) also needed to stay a genuine two-step
    negation (`s32 negOne = 1; negOne = -negOne;`) rather than a literal
    `-1` - the literal collapses to the *same* `0xff` byte already
    sitting in the previous store's register and gets reused outright,
    dropping the ROM's two real instructions.
- **`src/audio/gax_sound_handler_unknownc.c`** (`nullsub_41`,
  `sub_803A22C`, `nullsub_42`) - resolves three more entries in
  docs/audio.md's GAX2_SoundHandler per-type function-pointer table:
  `sub_803A22C` is the "UnknownC" type's `init_fn` (`0x0803A22D`) and
  `nullsub_42` its `unknown_fn` (`0x0803A275`), both confirmed by address
  (`+1` for the Thumb bit) against the table docs/audio.md already
  records; `play_fn` (`sub_803A324`) is still raw. `nullsub_41` sits
  immediately before this cluster but genuinely isn't part of the trio -
  no caller anywhere in the ROM (checked every `asm/*.s`, `expected/*.s`,
  and `src/` source file for a reference to it).
  - `sub_803A22C` loops a "songPtr" object's child array (`self+8`,
    `self->0xc` count, initialized to `1` first) and fires each entry's
    own function pointer through the `sub_803AD7C` trampoline - the loop
    bound extends by `self->0x14` only when
    `gUnknown_03001630->curChannelIdx == 0`; matches
    `docs/audio.md`'s "UnknownC children array" note. The two-armed
    bound computation needed the *inverse* `if`/`else` polarity from
    the obvious reading (write the `curChannelIdx == 0` arm as the
    `if`, not the `!= 0` one) to get gcc to emit `bne` (jump to the
    simple case) with the addition case as the fall-through, matching
    the ROM; and the addition itself needed the loop-bound variable
    pinned to `r0` (`register u32 limit asm("r0")`) with the two operands
    read as two separate statements in the ROM's own order (pointer
    chase first, `self->0x14` second) to land the `adds r0, r0, r1`
    Thumb encoding on the nose instead of a reg-swapped equivalent.

## Left raw (not attempted, or attempted and set aside)

- `sub_8039658`, `sub_80398DC` - many-register (`r8`/`sb`) allocation
  ceiling, same shape as `sub_8038538`'s cluster (issue #67); not
  attempted.
- `sub_803985C` - fully read and partially reconstructed (a voice-object
  field-reset-and-rebind routine, see the ROM's own field layout in the
  raw `asm/code_3_2_20e_985c.s`), but the ROM's real register allocation
  keeps reloading `self->0x3c` from memory three separate times across
  the function body rather than caching it, and reuses `ip`/`r0`/`r1`/`r3`
  in a pattern this pass couldn't reproduce byte-exact after several
  honest attempts (each fix for one instruction's register choice
  regressed a different one, adding an extra callee-saved register the
  ROM doesn't spend) - set aside rather than force a low-confidence pin.
- `sub_8039AA4`, `sub_8039B44`, `sub_8039E50` - `sub_8039B44`/
  `sub_8039E50` are one logical routine split by a manual
  compute-the-return-address-then-`bx` trampoline (the same idiom
  documented for `sub_803A278`/`sub_803A318` below), `sub_8039AA4` calls
  into both plus the newly-matched `sub_8039FFC`/`sub_803A03C`; not
  attempted this pass given the size and entanglement.
- `sub_803A03C` - many-register (`r8`) allocation ceiling; not attempted.
- `sub_803A158` - many-register (`r8`/`sb`/`sl`) allocation ceiling, a
  near-duplicate of the matched `sub_80395A4`/`sub_8039658` calling
  pattern but wider; not attempted.
- `sub_803A278`, `sub_803A2C8`, `sub_803A318` - three functions linked by
  the same manual return-address trampoline idiom noted above:
  `sub_803A278`'s tail computes a return address into `lr` and `bx`-jumps
  into a callee, landing back at its own cleanup block; `sub_803A2C8`
  does the same but its *return* lands inside `sub_803A318`'s own
  epilogue (`add sp,#0x3c; pop {r4,r5,r6}; pop {r0}; bx r0`), i.e. the
  two functions share one physical epilogue in the ROM - not reproducible
  as two independent C functions without hand-matching that fused tail;
  not attempted.
- `sub_803A324` - the "UnknownC" type's `play_fn`; many-register
  allocation ceiling (confirmed via isolated compile of a first-pass
  reconstruction); not attempted further.
- `sub_803A5A8`, `sub_803A608` - another return-address-trampoline pair,
  same shape as `sub_803A278`/`sub_803A318` above; `sub_803A608` is also
  the 2-instruction stub immediately in front of the raw ARM-mode DSP
  block docs/audio.md already documents (`gStaticData_0803A630` onward) -
  not attempted.

## A gotcha worth restating from `docs/workflow.md`

Two of this pass's four eventually-matched functions (`sub_8039818`,
`sub_8039FFC`) initially looked byte-identical in an **isolated**
compile and were provisionally written up as matched, then failed the
real full-ROM `make compare` by a handful of bytes once linked against
everything else - `sub_8039818`'s `cmd > 1` unsigned-vs-signed branch
condition, and `sub_8039FFC`'s table-lookup operand-hoisting register
swap. Neither difference was visible from the isolated `.s` output
alone without very close instruction-by-instruction comparison; both
were only actually caught by diffing the linked `crashbandicootxs.gba`
directly against `baserom.gba` (`cmp -l`) and mapping the differing file
offsets back to ROM addresses. This is exactly the failure mode
`docs/workflow.md` already warns about (citing `sub_8008C80`/
`sub_8008D30` and `sub_8009AA0`/`sub_8009B3C`) - a third and fourth data
point for "isolated compile is a diagnostic tool, never proof."
