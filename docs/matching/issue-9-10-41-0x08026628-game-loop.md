# `sub_8026628` (game_loop): matched, closing a cross-referenced gap from issues #9/#10/#41

Dedicated deep-investigation session against `sub_8026628` (ROM
`0x08026628`), independently flagged "still unexamined" from two
already-closed call sites earlier this session:

- `sub_8009BE0`'s doc
  ([naked-spatial-grid-tail.md](./naked-spatial-grid-tail.md)) calls it
  "a physics/collision step-probe function ... probes it via
  `sub_8026628` (also still unexamined)".
- `sub_800AAEC`'s doc
  ([issue-9-10-0x0800aaec-graphics.md](./issue-9-10-0x0800aaec-graphics.md))
  says it "gates the whole loop on a `sub_8026628` proximity probe
  against the player, built from self's own `self+0x20`-table[x]
  record's `+6` (s16) vertical offset and `self+0x28` bit 4 (mirror-
  flag) as a 1/2 selector."

`docs/rom_map.md` (line ~2472) had also already sketched it in passing
as "an umbrella 5-mode dispatcher unifying the already-documented
`sub_8026AE8`/`sub_8026A18` collision resolvers under one API." This
session confirms that shape (with one correction: 4 real dispatch
arms, not 5) and closes the function as real matched C.

## Bounds

`sub_8026628` sat in the middle of the still-fully-raw
`asm/code_3_2_17_25fc8.s` (per `tools/report_units.py`'s existing
comment: "the remainder of this stretch (`sub_8025FC8` onward) stays
genuinely raw"). Reading the file's `thumb_func_start` labels pinned
its exact extent: `sub_8026628` (line 924 of the old file, `@
0x08026628`) through the instruction right before `sub_80266BC` (line
1010, `@ 0x080266BC`) - **148 bytes** (`0x94`), comfortably inside the
"attempt a full match" size band this investigation's brief called for.

## Semantics

```c
s32 sub_8026628(void *self, s32 mode, struct probe_pos *pos, s32 span, s32 *outValue);
```

`pos` is a plain `{s32 x; s32 y;}` pair - confirmed against
`sub_800AAEC`'s own call site (`actor_part108.c`), which builds it from
a truncated Q8->int `{x, y}` and passes `&probe.x`/`&probe.origY` as
`pos`/`outValue` respectively. `span` is a plain scalar (`sub_800AAEC`
passes a hitbox record's raw `+9` byte, `sub_8009BE0` a value computed
by `sub_8008278`); `outValue` receives a push-out delta on a hit, but
neither of this session's two cross-referenced callers ever reads it
back afterward - they only check the `u8`-truncated return value.

`mode` selects one of two axis resolvers, with three of the four real
arms short-circuiting via a `self+0x10`-pointed bounds record before
ever running the tile scan:

- **`mode == 2`**: if `pos->x < 0`, clamps `*outValue = 0` and reports
  a hit immediately (the probe is already off the left edge of
  whatever region is loaded - nothing to scan). Otherwise calls
  `sub_8026AE8(self, pos, span, outValue, 3)`.
- **`mode == 1`**: reads `self+0x10`'s pointed-to record's own `+0x10`
  field (named `bounds->maxX` in the matched C - a right/loaded-region
  edge in the same plain-int units as `pos`, not Q8). If `pos->x` is
  past it, clamps `*outValue = bound << 8` and reports a hit without
  scanning. Otherwise calls `sub_8026AE8(self, pos, span, outValue, 1)`.
- **`mode == 4`**: always calls `sub_8026A18(self, pos, span,
  outValue, 2)` - no short-circuit for this arm (the one asymmetry
  among the four).
- **`mode == 8`**: the same shape as `mode == 1` but on the Y axis
  (`bounds->maxY` vs `pos->y`), calling `sub_8026A18(self, pos, span,
  outValue, 0)` when not already past the bound.
- any other `mode` value (in practice only `0`, per every known
  caller): returns `0` with no side effects - this is the "5th" arm
  `docs/rom_map.md`'s original "5-mode" framing was counting; it's a
  no-op default, not a real dispatch target.

### `sub_8026AE8`/`sub_8026A18`: which axis each one actually resolves

Both are still raw (`asm/code_3_2_17_266bc.s`, not in this session's
scope), but reading their own bytes alongside this dispatcher resolves
an ambiguity `docs/rom_map.md`'s original note left open ("a
horizontal/vertical collision-resolver pair" without saying which is
which):

- **`sub_8026A18`** scans `pos->x` over `[x, x+span-1] >> 3` at a
  **fixed** `pos->y >> 3` tile row, calling
  `sub_8025130(self->0x20, tileX, fixedTileY, submode, &scratchFlag)`
  per tile (matched, `src/system/game_loop3.c`). A horizontal *row*
  scan is how you detect floor/ceiling tiles under or above an object
  - i.e. this is the **Y-axis (vertical-position) resolver**, matching
  this function's own `mode == 4`/`8` pairing above. On a hit, it
  accumulates `±(tile_edge_distance << 8)` into `*outValue` using
  `pos->y & 7` - `submode 0` pushes up (`+(8-(y&7))<<8`), `submode 2`
  pushes down (`-(y&7)<<8`).
- **`sub_8026AE8`** scans `pos->y` over the same span at a **fixed**
  `pos->x >> 3` tile column - a vertical *column* scan, i.e. wall
  detection - the **X-axis (horizontal-position) resolver**, matching
  `mode == 1`/`2` above. On a hit it accumulates using `pos->x & 7`:
  `submode 1` pushes left (`-1-(x&7)<<8`), `submode 3` pushes right
  (`+1+(8-(x&7))<<8`, the `+1` an epsilon term the Y-axis resolver's
  own push doesn't have).

So `mode`'s four values map to each resolver's own `submode` argument
as `1->1`, `2->3`, `4->2`, `8->0` - non-monotonic, and this function's
dispatch just hard-codes each mapping per arm rather than deriving it
arithmetically from `mode`.

### Confirming against both cross-referenced callers

- `sub_800AAEC` passes `self+0x28` bit 4 (mirror flag) as a `1`/`2`
  selector - exactly this function's two X-axis (`sub_8026AE8`) arms,
  confirming `mode` really is a small enumerated direction selector
  (not a runtime-OR'd bitmask - its four handled values happen to be
  powers of two, but no known caller combines them).
- `sub_8009BE0` passes a plain-int (not Q8) position it just computed
  via `sub_8008278`, matching `pos`'s confirmed units here.

Read together with `sub_8025130`/`sub_8026AE8`/`sub_8026A18`, this is
a small "probe one axis for a solid tile in the direction `mode`
selects, short-circuiting against a cached loaded-region bound when
possible" API - `docs/rom_map.md`'s "umbrella API" framing was
directionally right, just overcounting the dispatch arms by one (the
default/no-op case isn't really a 5th mode).

## Matching

Matched as real C on the **first isolated-compile attempt** - no
register pins, opaque `asm volatile` anchors, or statement-order
juggling needed. The straightforward `switch (mode)` C reconstruction
(register-arithmetic version first, then a "prefer structs" pass
wrapping `pos`/`self+0x10`'s target in named structs per this
project's standing project-wide instruction) both produced assembly
byte-identical to the ROM's own instructions, operand for operand and
register for register - confirmed via the isolated
`cpp`/`agbcc`/`as` + `objcopy`/`cmp` pipeline against `baserom.gba`'s
raw bytes at `0x08026628`-`0x080266BC` (the only differences were the
three `bl sub_8026AE8`/`sub_8026A18` relocation sites, which resolve
correctly once linked) plus a full clean `rm -rf build && make
NON_MATCHING=1 report` (no warnings) and `rm -rf build
crashbandicootxs.elf crashbandicootxs.gba crashbandicootxs.map && make
compare` (`crashbandicootxs.gba: La suma coincide`).

One small fix was needed for the function's own trailing bytes: the
ROM pads `sub_8026628`'s end with a genuine zero-byte `.align 2, 0`
(already flush to a 4-byte boundary at `0x94` total, but the ROM's own
`.align 2, 0` directive still emits `0x0000` there) rather than the
assembler's default inter-function NOP-like padding (`mov r8, r8`,
`0x46c0`) - the established `matching_decomp_alignment_fix` idiom
(trailing `asm(".align 2, 0")` right after the function) reproduces
it exactly.

## Techniques used

- No register pins or opaque asm needed - a plain `switch` statement
  with `struct`-typed parameters (`struct probe_pos { s32 x; s32 y; }`
  and a small `struct sub_8026628_bounds` for the `self+0x10`-pointed
  record's two confirmed fields) reproduced the ROM's instructions
  exactly, per this project's standing "prefer structs over raw
  pointer-arithmetic casts" instruction - verified not to change
  codegen versus the raw-offset-cast draft this session also compiled
  first (byte-identical output either way).
- Trailing `asm(".align 2, 0")` for the zero-byte end-of-function
  padding gap (`matching_decomp_alignment_fix` precedent).
- Standard raw-asm-file split ("everything before, everything after")
  to carve the matched function out of a still-genuinely-raw file
  without disturbing its neighbors.

were already fully derived above (the "which axis each one actually

One small addition the earlier pass's semantic write-up didn't spell
out: both resolvers' final tail step (writing `self+0x29` from the
scan's own scratch out-flag when `self+0x2a` is set) is gated on the

only the final iteration's value survives to this check. Also: the
`self+0x20`-pointed `struct tile_cache`'s `unk010`/`unk014` fields
(`game_loop3.c`, previously commented "not read anywhere in this
cluster") are genuinely read here as this pass's end-index clamp bound

`game_loop3.c`'s own file is out of this pass's scope, but noted here

### Real C attempted first, briefly

Following this project's standard workflow, a straightforward C
reconstruction was attempted before falling back to NAKED:

1. **Unpinned, struct-typed** (`self+0x20` hoisted into a `struct
   tile_cache *cache` local before the loop, per this project's
   standing "prefer structs" instruction): compiled, but the register
   allocator put `self` on the stack (`str r0, [sp, #8]`) instead of
   `sl`, freed `r6` for the hoisted `cache` local (which the ROM
   itself never does - it re-derives `self->0x20` fresh from `sl`
   every loop iteration instead of caching it across the `bl
   sub_8025130` call), and spilled `tileY` to the stack instead of
   keeping it in a register.
2. **Unpinned, raw-offset casts** (no `cache` local - `self->0x20`
   dereferenced fresh inline at every use site, matching the ROM's own
   redundant-reload shape): closer - `self` still landed in `r8`
   rather than `sl`, `pos`/`outValue` landed in `r6`/`r7` rather than
   `r7`/`r8`, and `submode` got hoisted into a resident `sb` register
   rather than staying purely stack-resident (reloaded via `ldr` from
   its incoming stack slot on every use, which is what the ROM does).
3. **Register-pinned** (`self`/`pos`/`outValue`/`hit` pinned to
   `sl`/`r7`/`r8`/`sb` via `register ... asm("...")` locals, matching
   `matching_decomp_register_pinning`'s established recipe): made
   things *worse*, not better - the same symptom `game_loop3.c`'s own
   `sub_8024F24` comment already documented for this exact bug class.
   With `pos` pinned to `r7`, the compiler stopped treating it as a
   live base-pointer register at one call site and instead emitted
   `add r3, r7, #0` (passing `pos` itself as `sub_8025130`'s `mode`
   argument) where the ROM has `ldr r3, [sp, #0x2c]` (reloading the
   real `submode` value from its stack slot) - a genuine
   mis-optimization/miscompile risk, not just a relocation-site or
   register-numbering difference.

Recognized this as the same register-allocation-permutation gap
already forced NAKED on `sub_8025130`/`sub_8025228`/`sub_8025460`
(`game_loop3.c`/`game_loop4.c`) and `sub_8024F24` right next door,
per this session's own explicit guidance not to over-invest in
fighting it further, and moved directly to a NAKED transcription for
both functions.

### NAKED transcription

Both closed as hand-transcribed NAKED functions
(`src/system/game_loop46.c`, new file), instruction for instruction
from the ROM's own disassembly (`0x08026A18`-`0x08026BC0`, 424 bytes
total), translating unified-syntax mnemonics to this project's
established divided/suffix-less convention (`adds`->`add`,
`movs`->`mov`, `subs`->`sub`, `asrs`->`asr`, `ands`->`and`,
`lsls`->`lsl`, `rsbs r0, r0, #0`->`neg r0, r0`) and GNU-as local
numeric labels (`1:`/`1f`/`1b` etc.) in place of the ROM disassembly's
own `_080xxxxx` global labels.

Confirmed byte-identical to `baserom.gba`'s own raw bytes at
`0x08026A18`-`0x08026BC0` via the isolated `cpp`/`agbcc`/`as` +
`objcopy`/`cmp` pipeline - the only differences were the two `bl
sub_8025130` relocation sites (`0x08026A70`, `0x08026B40`), which
resolve correctly once linked - plus a full clean `rm -rf build &&
make NON_MATCHING=1 report` (no warnings) and `rm -rf build
crashbandicootxs.elf crashbandicootxs.gba crashbandicootxs.map && make
compare` (`crashbandicootxs.gba: La suma coincide`).

Both functions end already flush to a 4-byte boundary (208 B/216 B
respectively) but the ROM's own trailing `.align 2, 0` still emits a
genuine zero-byte `0000` halfword there (confirmed via objdump against
the raw ROM bytes, not the assembler's default `mov r8, r8`
inter-function padding) - the same `matching_decomp_alignment_fix`
idiom `sub_8026628` itself needed, reproduced with a trailing
`asm(".align 2, 0")` after each function.

### Techniques used

- Hand-transcribed NAKED asm, the established escape hatch for this
  exact gcc-2.9 register-allocation-permutation gap (see

  precedent).
- Standard raw-asm-file trim ("everything before this pass's two
  functions stays, everything from them onward is extracted") to
  carve the matched functions out of a still-genuinely-raw file
  without disturbing its other neighbors.
